# Как заявки попадают в Битрикс24

Браузер отправляет заявку не в Битрикс, а на наш сервер. Сервер уже своим ключом
создаёт лид штатным методом `crm.lead.add` и получает его номер.

```
браузер ──POST /api/lead──▶ nginx ──proxy──▶ сервис приёма ──crm.lead.add──▶ Битрикс24
   JSON                    map.product1c.ru   127.0.0.1:8123                  лид № 8045
```

## Почему не напрямую в CRM-форму

Первая версия обращалась к точке приёма CRM-формы `crm.site.form.fill`. Лиды при
этом создавались пустыми. Причин три:

1. **Форма настроена как форма заказа с оплатой.** Ответ содержит `"pay":true` и
   редирект на оформление заказа: она ждёт товарную корзину, а не заявку.
2. **Точка приёма недокументирована и не проверяет данные.** Она отвечает
   «успех» на что угодно — неверные имена полей, неверные типы, лишние поля.
   Ошибку не вернёт, поэтому убедиться, что данные дошли, невозможно.
3. **Состав полей меняется при правке формы.** Прежние имена (`CONTACT_NAME`,
   `CONTACT_EMAIL`) исчезли — а код об этом не узнал, потому что ошибок нет.

`crm.lead.add` лишён всех трёх проблем: документирован, поля называются явно, в
ответ приходит номер созданного лида — результат проверяем.

## Ключ доступа

Нужен входящий вебхук: **Битрикс24 → Приложения → Разработчикам → Другое →
Входящий вебхук**, право **CRM**. Выглядит так:

```
https://<портал>.bitrix24.ru/rest/<id>/<токен>/
```

Вебхук даёт доступ ко всей CRM, поэтому он **не хранится в коде и не попадает в
git**. Файл на сервере:

```
/etc/karta1c/bitrix-webhook   права 600, владелец root
```

Сервис читает файл при каждом запросе — замена ключа не требует пересборки,
достаточно перезаписать файл и перезапустить юнит. В логи и в ответы API ключ
не попадает: пишутся только номер лида и адрес отправителя.

Если ключ где-то засветился (переслали в чате, вставили в тикет) — выпустите
новый в Битриксе и замените файл. Старый перестаёт работать сразу.

## Что уходит в лид

| Поле Битрикса | Откуда |
|---|---|
| `TITLE` | «Карта 1С — комплект» или «Карта 1С — <название продукта>» |
| `NAME` | имя из формы |
| `PHONE` | телефон из формы |
| `EMAIL` | почта, если заполнена |
| `IM` | мессенджер, если заполнен |
| `COMMENTS` | состав комплекта, суммы, расчёт мест, оговорки, комментарий клиента |
| `SOURCE_ID` | `WEB` |
| `SOURCE_DESCRIPTION` | «Карта продуктов 1С» |

Пример комментария:

```
Конфигурации: 1С:Бухгалтерия, 1С:УНФ
Сервисы: 1С:ИТС, 1С-Отчётность
Размещение: Коробка на компьютере
Рабочие места: 2 места уже в поставках, докупаем 8 — итого 10 на 10 человек.
Разовая покупка: 113 600 ₽
Подписки в год: 68 400 ₽
Покрыто подпиской ИТС: 1С-Отчётность
Статус расчёта: предварительный, требует подтверждения специалистом
Размер компании: 10 чел.

Комментарий клиента:
…

Источник: map.product1c.ru
```

Менеджер видит, что человек уже собрал, и не начинает разговор с нуля.

## Сервис приёма

Небольшой сервис на стандартной библиотеке Python, слушает только `127.0.0.1` —
снаружи доступен исключительно через nginx по пути `/api/lead`.

| Что | Где |
|---|---|
| Юнит | `karta1c-lead.service` |
| Ключ | `/etc/karta1c/bitrix-webhook` |
| Лог | `/var/log/karta1c-lead.log` |
| Здоровье | `GET /api/lead/health` |

Защита: не больше 12 заявок с адреса за 10 минут, скрытое поле-ловушка от ботов,
потолок размера запроса, обязательные имя и телефон.

```bash
curl -s https://map.product1c.ru/api/lead/health
# {"ok":true,"configured":true} — сервис поднят и ключ на месте
```

`"configured": false` означает, что файла с ключом нет: заявки уйдут по
запасному пути.

## Запасной путь

Если сервис недоступен, форма молча уходит на точку приёма CRM-формы. Лид
создастся, но беднее: полей «Имя» и «E-mail» в форме может не быть, и всё
уезжает в комментарий. Это страховка от потери заявки, а не рабочий режим.
